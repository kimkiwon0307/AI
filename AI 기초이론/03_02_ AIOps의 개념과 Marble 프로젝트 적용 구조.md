
# AI 기초 이론 — 3장 2교시
## AIOps의 개념과 Marble 프로젝트 적용 구조

### 1. AIOps란 무엇인가?

AIOps(Artificial Intelligence for IT Operations)는 **AI 기술을 IT 인프라 운영에 활용하는 것**이다.

기존 모니터링과 자동화 기술에 AI를 결합하여 장애 분석과 대응 업무를 효율화한다.

대표적인 기능:
- 장애 감지 및 이상 징후 분석
- 장애 로그·메트릭 자동 수집
- 여러 장애 이벤트의 연관성 분석
- AI 기반 장애 원인 가설 생성
- 장애 대응 방법 추천
- 조건부 자동 복구 및 결과 검증

**핵심:** AIOps는 AI가 모든 장애를 해결하는 기술이 아니라, AI를 이용해 IT 운영을 지원하고 일부 작업을 자동화하는 방식이다.

---

### 2. 기존 모니터링과 AIOps의 차이

#### 기존 Marble 운영 방식

```text
Marble 서버 장애 발생
         ↓
Zabbix 장애 감지
         ↓
Discord 장애 알림
         ↓
운영자가 로그 확인
         ↓
원인 분석 및 복구
```

#### AIOps 적용 후 목표

```text
Marble 서버 장애 발생
         ↓
Zabbix 장애 감지
         ↓
Python 장애 정보 자동 수집
         ↓
AI 장애 원인 분석
         ↓
복구 정책 및 안전 조건 확인
         ↓
허용된 단순 장애 자동 복구
         ↓
정상 여부 검증 및 Discord 알림
```

| 구분 | 기존 운영 | AIOps 적용 |
|---|---|---|
| 장애 감지 | Zabbix | Zabbix |
| 로그 확인 | 운영자 수동 확인 | Python 자동 수집 |
| 원인 분석 | 운영자 직접 분석 | AI가 원인 분석 지원 |
| 복구 방법 | 운영자 판단 | AI가 대응 방법 추천 |
| 복구 실행 | 운영자 직접 실행 | 일부 조건부 자동 실행 |
| 복구 검증 | 운영자 확인 | Health Check 자동 검증 |

**핵심:** 기존에는 장애 감지와 알림이 중심이었다면, AIOps는 분석·대응·검증까지 자동화 범위를 확장한다.

### 3. AIOps의 전체 동작 원리

```text
① 장애 감지
       ↓
② 장애 정보 수집
       ↓
③ AI 원인 분석
       ↓
④ 복구 가능 여부 판단
       ↓
⑤ 자동 복구 또는 운영자 승인 요청
       ↓
⑥ 복구 결과 검증
       ↓
⑦ 알림 및 장애 이력 저장
```

#### ① 장애 감지

Zabbix가 CPU·메모리·서비스 상태 등의 이상을 감지한다.

#### ② 장애 정보 수집

Python이 다음 정보를 수집한다.

- 장애 발생 서버와 시각
- 관련 오류 로그
- CPU·메모리 등 메트릭
- 최근 Jenkins 배포 이력
- 서비스 및 네트워크 연결 상태

#### ③ AI 원인 분석

수집한 정보를 Ollama에서 실행되는 Qwen에 전달한다.

AI는 가능한 장애 원인과 추가 확인 방법을 생성한다.

#### ④ 복구 판단

Python 복구 정책 엔진이 실제 상태와 안전 조건을 검사한다.

AI의 답변만으로 복구를 결정하지 않는다.

#### ⑤ 복구 실행

안전 조건을 만족하는 단순 장애만 사전 정의된 명령으로 복구한다.

위험한 장애는 운영자 승인을 요청한다.

#### ⑥ 결과 검증

서비스 재시작 이후 실제 정상 여부를 확인한다.

예:
- systemd 서비스 상태
- TCP 포트 연결
- `/health` 응답
- ALB Target Health

#### ⑦ 알림 및 기록

Discord로 분석 결과와 복구 상태를 알리고 장애 이력을 저장한다.

### 4. AIOps에서 AI가 담당하는 역할

AI가 수행하기에 적합한 작업:

1. 여러 줄의 장애 로그 요약
2. 장애 원인 후보 제시
3. 관련 장애 정보 분석
4. 추가 확인 방법 추천
5. 장애 대응 가이드 작성

#### 예시

WAS01에서 다음 오류가 발생했다.

`Communications link failure`

AI가 제시할 수 있는 원인 후보:

- MySQL 서비스 중단
- DB 3306 포트 차단
- Security Group 설정 문제
- 네트워크 연결 장애
- MySQL 리스닝 설정 문제

AI는 가능성이 높은 원인을 추론하지만 실제 장애 원인을 확정하지는 못할 수 있다.

**중요:** AI가 생성한 내용은 실제 서버 상태와 비교하여 반드시 검증해야 한다.

---

### 5. 장애 자동 복구는 어떻게 이루어지는가?

자동 복구는 AI가 직접 임의의 명령을 실행하는 방식이 아니다.

**AI는 장애를 분석하고, Python 복구 정책 엔진이 사전에 허용된 조건과 명령에 따라 복구를 수행한다.**

#### 자동 복구가 가능한 예

| 장애 유형 | 복구 방법 |
|---|---|
| WAS 프로세스 단순 중단 | 조건 충족 시 서비스 재시작 |
| Apache 서비스 단순 중단 | 조건 충족 시 서비스 재시작 |
| 일시적인 서비스 응답 오류 | 상태 재확인 및 사전 정의된 점검 |

예를 들어 WAS01의 Spring Boot 서비스가 중단되었다면 다음 명령으로 재시작할 수 있다.

```bash
sudo systemctl restart marble
```

단, 명령 실행 전에 안전 조건을 확인해야 한다.

#### 자동 복구에 신중해야 하는 장애

| 장애 유형 | 권장 대응 |
|---|---|
| MySQL Primary 장애 | 운영자 확인 및 수동 복구 |
| DB 복제 장애 | 복제 상태 분석 후 조치 |
| AWS 네트워크 장애 | 원인 분석 및 운영자 조치 |
| Jenkins 배포 후 장애 | 분석 후 승인 기반 롤백 |

**핵심:** 단순하고 위험도가 낮으며 복구 결과를 검증할 수 있는 장애부터 자동화한다.

---

### 6. 자동 복구에 필요한 안전장치

자동 복구 시스템에는 다음 조건이 필요하다.

#### ① 허용된 명령만 실행

사전에 승인한 복구 명령만 실행한다.

AI가 임의로 생성한 Linux 명령어를 그대로 실행하지 않는다.

#### ② 복구 전 상태 확인

- 서비스가 실제로 중단되었는가?
- 다른 WAS 서버는 정상인가?
- DB 등 공통 장애가 아닌가?
- 기존 systemd 자동 재시작과 중복되지 않는가?

#### ③ 재시도 횟수 제한

동일한 장애가 반복되더라도 무한 재시작하지 않는다.

예: 자동 재시작 최대 1~2회 후 운영자에게 알림

#### ④ 복구 후 검증

서비스를 재시작한 것만으로 복구 성공이라고 판단하지 않는다.

`/health` 및 실제 서비스 상태를 확인한다.

#### ⑤ 장애 이력 저장

다음 정보를 기록한다.

- 장애 발생 시간
- 장애 서버와 유형
- AI 분석 결과
- 실제 실행한 명령어
- 복구 성공 및 실패 여부

### 7. Marble AIOps 최종 아키텍처

```text
Marble AWS 3-Tier
 WEB01/02 · WAS01/02 · DB Primary/Replica
                    |
                    v
              Zabbix 장애 감지
                    |
                    v
              Webhook 이벤트 전송
                    |
                    v
           Python AIOps 프로그램
                    |
          +---------+---------+
          |         |         |
          v         v         v
      Zabbix API   ELK    Jenkins API
       메트릭     오류 로그   배포 이력
          |         |         |
          +---------+---------+
                    |
                    v
             장애 증거 통합
                    |
                    v
              Ollama + Qwen
                    |
                    v
          AI 원인 가설 및 대응 추천
                    |
                    v
            Python 복구 정책 엔진
                    |
            안전 조건 검증
                    |
          +---------+---------+
          |                   |
          v                   v
      자동 복구 가능       자동 복구 불가
          |                   |
          v                   v
     복구 스크립트 실행    운영자 알림
          |
          v
      Health Check
          |
          v
     Discord 알림 + 이력 저장
```

#### 구성 요소별 역할

| 기술 | 역할 |
|---|---|
| AWS | Marble WEB/WAS/DB 인프라 |
| Zabbix | 장애 감지 |
| Webhook | 장애 이벤트 자동 전달 |
| ELK | 로그 수집·저장·검색 |
| Jenkins API | 최근 배포 이력 조회 |
| Python | 정보 수집 및 전체 자동화 흐름 제어 |
| Ollama | AI 모델 실행 환경 |
| Qwen | 장애 원인 분석 및 대응 방법 생성 |
| 복구 정책 엔진 | 안전 조건 확인 및 복구 실행 |
| Discord | 장애 분석·복구 결과 알림 |

위 아키텍처는 앞으로 구현할 목표이며 현재 모든 기능이 완성된 상태는 아니다.

### 8. 실제 Marble 장애 시나리오

#### 상황: WAS01에서 DB 연결 실패

오류 로그:

`Communications link failure`

#### AIOps 동작 과정

1. Zabbix가 WAS01 장애 감지
2. Python이 장애 이벤트 수신
3. ELK에서 관련 오류 로그 조회
4. Zabbix에서 WAS·DB 상태 확인
5. Jenkins에서 최근 배포 이력 조회
6. Qwen이 가능한 장애 원인 분석
7. Python이 실제 상태와 안전 조건 검증
8. 복구 가능 여부 판단
9. 위험한 DB 관련 조치는 운영자에게 전달
10. Discord 알림 및 분석 결과 저장

이렇게 하면 운영자는 장애 발생 사실뿐 아니라 가능한 원인과 확인해야 할 사항을 함께 전달받을 수 있다.

### 9. AIOps의 한계

AIOps가 모든 장애를 자동으로 해결하는 것은 아니다.

- AI는 잘못된 원인을 제시할 수 있다.
- 로그·메트릭이 부족하면 분석 품질이 떨어진다.
- 자동 복구가 오히려 장애를 확대할 수 있다.
- 복구 정책과 검증 절차가 필요하다.
- AI 서버 자체에도 장애가 발생할 수 있다.

따라서 AI 분석이 실패하더라도 기존 Zabbix 알림 기능은 유지되도록 설계하는 것이 좋다.

**핵심:** AIOps는 AI 모델만 설치하는 것이 아니라 모니터링, 자동화, 운영 정책, 검증을 결합하는 시스템이다.

### 10. 핵심 개념 최종 정리

| 개념 | 설명 |
|---|---|
| AIOps | AI를 IT 운영에 활용하는 분야 |
| 장애 감지 | Zabbix 등으로 시스템 이상 확인 |
| 장애 상관분석 | 여러 이벤트 사이의 관련성 분석 |
| AI 원인 분석 | 로그와 상태를 이용한 원인 가설 생성 |
| Runbook | 장애 대응을 위해 미리 정의한 절차 |
| 자동 복구 | 허용된 조건에서 복구 작업 실행 |
| 복구 정책 | 자동 실행 가능 여부를 판단하는 규칙 |
| Health Check | 복구 후 서비스 정상 여부 확인 |
| 장애 이력 | 장애 분석·실행·복구 결과 기록 |

### 반드시 기억할 핵심 5가지

1. **AIOps는 AI를 IT 운영에 적용하는 방식이다.**
2. **AIOps는 장애 감지뿐 아니라 분석·대응·검증까지 자동화 범위를 확장한다.**
3. **AI는 장애 원인 가설과 대응 방법을 제시하지만 항상 정확하지는 않다.**
4. **자동 복구는 사전에 허용한 명령과 안전 조건을 충족하는 경우에만 실행한다.**
5. **Marble AIOps에서는 Python이 중심이 되어 Zabbix·ELK·Jenkins·Ollama·Qwen을 연결한다.**

### 11. 복습 확인문제 및 정답

**Q1. AIOps란 무엇인가?**

정답: AI 기술을 IT 인프라 운영의 장애 감지, 분석, 대응 등에 활용하는 분야이다.

**Q2. 기존 모니터링과 AIOps의 주요 차이는?**

정답: AIOps는 기존 감지·알림에 AI 분석과 대응 자동화 기능을 추가할 수 있다.

**Q3. AI가 장애 원인을 분석하면 바로 복구 명령을 실행해도 되는가?**

정답: 아니다. 실제 상태와 사전에 정의한 안전 조건을 검증해야 한다.

**Q4. 자동 복구에 필요한 안전장치는 무엇인가?**

정답: 허용 명령 제한, 복구 전 상태 확인, 재시도 제한, 복구 후 검증, 장애 이력 기록 등이 있다.

**Q5. Marble AIOps에서 Python의 역할은 무엇인가?**

정답: 장애 정보를 수집하고 AI 모델과 기존 인프라를 연결하며 자동 복구 과정을 제어하는 것이다.
